# SMC-стратегия: архитектура и эксплуатация

Документ описывает вторую стратегию бота — Smart Money Concepts, построенную
по методичке `SMC_strategy_crypto.md`. Фибоначчи в ней остаётся, но как
вспомогательный слой (premium/discount, OTE, цели по расширениям), а не как
основа сигнала.

Исходная фибо-стратегия никуда не делась и остаётся стратегией по умолчанию.

---

## 1. Где что лежит

```
Live_Bot/
  smc/                  ← ядро стратегии, чистый расчёт по свечам
    params.py           все настройки (env-префикс SMC_)
    swings.py           фрактальные свинги 3/5 баров          §2.1
    structure.py        HH/HL/LH/LL, BOS / mBOS / CHoCH, SMS  §2.2-2.5
    liquidity.py        BSL/SSL, EQH/EQL, PDH/PDL, снятия     §3
    imbalance.py        FVG и состояние его заполнения        §4
    poi.py              Order Block, Breaker, Mitigation, Wick §5
    fib.py              premium/discount, OTE, цели           §10, §22
    sessions.py         killzones, открытия, азиатский рендж  §11
    signal.py           сборка сетапа по чек-листу            §23
  strategy_smc.py       ← адаптер: ядро → формат trade_manager
  tests/                ← 37 тестов, включая сквозной на lookahead

research/
  smc_engine.py         честный портфельный движок бэктеста
  backtest_smc.py       сравнение SMC против фибо v3
  smc_sweep.py          перебор параметров
  smc_validate.py       проверка на устойчивость по полугодиям
```

### Почему ядро внутри `Live_Bot/`

По принятой модели деплоя папка `Live_Bot/` перезаписывается целиком. Пакет
`smc/`, лежащий снаружи, терялся бы при каждом обновлении сервера. Данные
по-прежнему живут отдельно, в `BOT_DATA_DIR`.

### Почему ядро не знает про биржу

`smc/` не импортирует ни `config.py`, ни `exchange.py`, ни `logger.py` — он
считает только по DataFrame свечей. Благодаря этому **один и тот же код**
работает в бою и в бэктесте. У фибо-стратегии логика была продублирована в
`Live_Bot/strategy.py` и `research/backtest.py`, и эти копии со временем
разошлись; здесь такая ситуация невозможна конструктивно.

## 2. Как принимается решение

Порядок повторяет методичку сверху вниз (§2.6: анализ от старших ТФ к младшим).

1. **Killzone** (§11.2) — если включён жёсткий режим, вне сессии не входим.
2. **Bias старшего порядка.** 1D задаёт направление, 4H уточняет. Если они
   противоречат — сделки нет. Это ровно ситуация «ложного слома структуры на
   младшем ТФ» из §2.3.
3. **Импульсная нога** на рабочем ТФ (1H) должна совпадать с bias. Если цена
   ушла за 88.6% коррекции — сетап инвалидирован (§22.2).
4. **Зона интереса** нужного направления, ещё не протестированная.
5. **Premium / discount** (§10.1): для лонга зона обязана быть в дисконте,
   для шорта — в премиуме. Умные деньги покупают со скидкой.
6. **Цена ещё не дошла до зоны** — лимит должен «отдыхать» впереди хода.
7. **Confluence** — сумма весов подтверждающих факторов (§23). Торгуем
   только сетапы, набравшие `MIN_CONFLUENCE_SCORE`.
8. **Геометрия**: вход в зоне, стоп за её экстремумом, цели по расширениям
   Фибоначчи и непротестированным пулам ликвидности (§14.2).
9. **Гейт по RR** (§16) и расчёт размера позиции (§15.2).

### Факторы confluence

| Фактор | Вес | Раздел |
|---|---|---|
| направление совпало со старшим ТФ | 1.0 | §2.6 |
| перед зоной снята ликвидность | 1.0 | §3.3, §5 |
| зона в правильной половине диапазона | 1.0 | §10.1 |
| зона не тестировалась ранее | 0.8 | §5 |
| был слом структуры в нашу сторону | 0.8 | §5.1 |
| рядом с зоной есть имбаланс | 0.6 | §4.2 |
| вход попадает в зону OTE | 0.5 | §10.1 |
| время входа внутри killzone | 0.5 | §11.2 |
| коррекция медленнее импульса | 0.4 | §10.3 |

## 3. Три дефекта, найденные при разработке

Все относятся к классу «результат выглядит правдоподобно, но неверен».

### Разметка смотрела в будущее

Свинг физически становится известен только через N свечей — правые бары ещё
не сформированы. Наивная реализация размечает свинг задним числом и
«принимает решения», зная будущее. В коде у каждого свинга есть поле
`confirmed_at`, и любой запрос состояния фильтруется по нему
(`visible_swings`, `state_at`, `visible_points`).

### Таймфреймы разъезжались из-за разрешения времени

pandas 3 хранит `datetime64` в том разрешении, в котором создана колонка.
`pd.to_datetime(..., unit='ms')` даёт `datetime64[ms]`, и `.astype('int64')`
возвращает **миллисекунды**, тогда как `Timestamp.value` — всегда
**наносекунды**. Сравнение таких чисел приводило к тому, что `align_index`
всегда возвращал последнюю свечу: bias читался **из конца истории**. На BTC
это давало ровно ноль сигналов за год.

Лечение — функция `signal.to_ns()` с явным `as_unit('ns')`. На баг есть
регрессионный тест: `test_to_ns_normalises_millisecond_resolution`.

### Bias читался по НЕЗАКРЫТОЙ свече старшего таймфрейма

Самый коварный из трёх. Дневная свеча текущего дня начинается в 00:00, её
метка времени МЕНЬШЕ текущего момента — и наивная проверка «метка <= сейчас»
её принимает. Но её high/low/close агрегируют весь день, включая часы,
которые ещё не наступили. Bias, посчитанный по такой свече, знает будущее.

Лечение — `align_index(df, ts, duration_ns=...)`: свеча старшего ТФ
считается доступной, только если `начало + длительность <= момента решения`.
Момент решения при этом — ЗАКРЫТИЕ текущей свечи рабочего ТФ, а не её
начало (метка времени по соглашению ccxt — время открытия).

Найден сквозным тестом `test_no_lookahead.py`, который сравнивает решение на
свече i при полной и обрезанной по i истории. Обычные юнит-тесты этот класс
ошибок не ловят: код не падает, а результаты бэктеста выглядят правдоподобно
— просто они недостижимы в реальности. Все числа, полученные до этого
исправления, были завышены.

## 4. Честный бэктест

`research/smc_engine.py` отличается от старого `research/backtest.py`
допущениями, каждое из которых меняет выводы, а не косметику:

| | старый движок | `smc_engine` |
|---|---|---|
| исполнение лимита | считается налитым сразу | только если цена дошла |
| комиссии | нет | maker 0.02% / taker 0.055% |
| проскальзывание стопов | нет | 0.05% против позиции |
| спорная свеча (SL и TP вместе) | по расстоянию от открытия | всегда в пользу стопа |

Первое допущение — самое важное: вход стоит на уровне, до которого рынок ещё
не дошёл, и часть таких сделок в реальности не открылась бы вовсе. В прогонах
SMC около 40% лимитных ордеров не наливаются.

Движок стратегия-агностичен, поэтому фибо-стратегия прогоняется через него
же — иначе сравнение измеряло бы разницу допущений, а не разницу стратегий.

### Проверка на смене режима — и что она изменила

Все цифры выше получены на бычьем периоде. Прогон на 2022-01 .. 2023-07
(обвал с крахом LUNA, дно с крахом FTX, боковик 2023) показал, что исходная
конфигурация SMC там **убыточна**: −8.3% при просадке 60.2% и PF 0.985.
Красивый profit factor на росте оказался свойством режима, а не метода.

Шесть попыток починить это изменением структуры стратегии провалились:
ближняя цель, младший таймфрейм, ослабление фильтров, отступ входа, фильтр
режима по подтверждённому тренду, направленный кэп. Каждая казалась
разумной; данные отвергли все.

Сработал седьмой подход — **разбор вкладов** (`research/smc_attribution.py`):
вместо угадывания структуры посмотреть, какие признаки сетапа статистически
связаны с результатом, и проверить это на обоих режимах сразу.

### Веса confluence были неверны

Выяснилось, что расставленные вручную по тексту методички веса частично
описывали шум:

| Фактор | Бычий (есть/нет) | Медвежий (есть/нет) | Было | Стало |
|---|---|---|---|---|
| ote_zone | +0.509 / +0.234 | +0.418 / −0.240 | 0.5 | **1.2** |
| structure_break | +0.343 / +0.192 | +0.032 / −0.336 | 0.8 | 0.8 |
| fvg_present | +0.353 / +0.190 | +0.033 / −0.281 | 0.6 | 0.6 |
| liquidity_swept | +0.292 / +0.393 | +0.039 / −0.011 | 1.0 | **0.3** |
| law_of_effort | +0.305 / +0.345 | +0.043 / +0.007 | 0.4 | **0.1** |
| killzone | +0.306 / +0.350 | −0.110 / +0.084 | 0.5 | **0.0** |

Самый сильный предиктор — попадание входа в зону OTE — имел вес 0.5 из 6.7
возможных, то есть почти не влиял на решение. А killzone, которому §11.2
отводит важную роль, оказался **отрицательным** предиктором на обоих
периодах: совет, разумный для живого трейдера (ограничить число решений за
день), для бота вреден — у него нет проблемы с концентрацией внимания.

### Результат пересчёта весов

Одно это изменение, без единой правки в структуре стратегии:

| | Бычий 25-26 | Медвежий 22-23 |
|---|---|---|
| Исходные веса | +417.6%, PF 1.447 | −8.3%, DD 60.2%, PF 0.985 |
| **Измеренные веса** | **+866.8%**, DD 24.9%, **PF 1.954** | **+82.7%**, DD 37.6%, **PF 1.151** |

Стратегия из убыточной на медвежьем рынке стала прибыльной и одновременно
вдвое выросла на бычьем. R на сделку поднялся с 0.337 до 0.548.

Вывод для методологии: проблема была не в управлении позицией, а в том, что
отбор сетапов работал наполовину случайно. Улучшать выходы при случайных
входах бессмысленно — именно поэтому шесть предыдущих попыток и не дали
ничего.

### Чего эти цифры НЕ доказывают

- **Период преимущественно бычий.** Обе стратегии торговали в основном
  лонги. О поведении в медвежьем рынке и затяжном боковике данные молчат.
- **Живой торговли не было.** Только бэктест.
- Около половины лимитных ордеров SMC не наливается (`no_fill=440` из 930
  на полном пуле) — этот параметр в модели легко оценить неверно, и
  проверять его нужно на демо-счёте.

## 7. Переключение стратегии в бою

Управляется переменной `STRATEGY` в `.env`:

```
STRATEGY=FIBO    # по умолчанию — исходная фибо-стратегия
STRATEGY=SMC     # стратегия Smart Money Concepts
```

По умолчанию стоит `FIBO`: переключение должно быть осознанным действием, а
не побочным эффектом обновления кода на сервере.

Параметры SMC переопределяются через окружение с префиксом `SMC_`, например:

```
SMC_MIN_CONFLUENCE_SCORE=4.5
SMC_MIN_RR=4.0
SMC_POI_TYPES=ORDER_BLOCK,MITIGATION
SMC_BREAKEVEN_AFTER_TP1=false
```

### План выхода принадлежит стратегии, а не боту

Аудит 2026-08-04 вскрыл тихий дефект: доли частичной фиксации, безубыток и
направленный кэп брались из глобального `config.py`, откалиброванного под
фибо-стратегию. SMC при этом закрывалась целиком на первой цели вместо
25/25/50, то есть работала в конфигурации, которая по её же бэктесту
убыточна (−9.1% против +40.6% на трёх целях): основную прибыль дают дальние
цели при винрейте около 25%. Безубыток применялся вопреки замеру, где он
снижает результат с +88.5% до +54.2%.

Причина структурная: с двумя одновременно работающими стратегиями одна
глобальная настройка обслужить обе не может в принципе. Решение —
план едет вместе с сигналом:

```python
params['tp_targets']         # все цели, включая третью
params['tp_fractions']       # доли, сумма ровно 1.0
params['breakeven_after_tp'] # переносить ли стоп в безубыток
params['max_same_direction'] # кэп позиций в одну сторону
```

Разбор — в `Live_Bot/exit_plan.py`, им пользуются оба исполнителя (боевой
`trade_manager` и фантомный `paper_broker`), при этом `paper_broker`
по-прежнему не импортирует код, умеющий отправлять ордера. План сохраняется
в состоянии позиции: после рестарта бота взять его больше неоткуда — биржа
таких данных не хранит. Сигналы без плана (сохранённые прошлой версией)
доигрываются по старым правилам.

Три цели теперь выставляются на бирже как отдельные `limit reduce_only`
по долям; тейк на ордере входа вешается только при единственной цели, иначе
биржевой TP закрыл бы всю позицию и обрубил дальние уровни.

## 8. Что осталось за рамками первого этапа

Реализовано ядро SMC. В методичке есть блоки, сознательно отложенные:

- паттерны TDP / TTS (§7), M/W, Stop Hunt, Turtle Soup (§13);
- рендж и девиации (§8), Power of Three (§12);
- схемы Вайкоффа (§9) — сама методичка предупреждает, что ложных схем
  больше, чем истинных, поэтому формализация требует отдельной проверки;
- RSI-дивергенции (§6);
- funding rate + open interest (§18.1) — данные есть у биржи;
- BTC.D / DXY / S&P 500 (§17) — требуют внешних источников данных;
- ликвидационные heatmaps, CVD, стакан (§18.2-18.3).

Каждый такой блок добавляется как новый фактор confluence и проверяется
бэктестом отдельно — добавлять их пачкой без проверки бессмысленно.
