# История изменений — Kraken Trading Bot

Файл ведётся автоматически. Каждое реальное изменение кода фиксируется здесь с датой.
Обсуждения и анализ сюда не заносятся — только факт внесённого изменения.

## [2026-06-28] — W11: Стратегия «Фибо-лимит» (конфиг D3 по бэктесту)

**Файлы:** `Live_Bot/config.py`, `Live_Bot/strategy.py`, `Live_Bot/pair_scanner.py`,
`Live_Bot/trade_manager.py`, `Live_Bot/trade_journal.py`, `Live_Bot/telegram_notify.py`,
`Live_Bot/chart_generator.py`, `Live_Bot/bot.py`, `Live_Bot/.env`, `backtest_campaign.py` (новый)

**Контекст:** 6-мес бэктест по методичке «Чек лист по Фибоначчи». Старая логика (BoS-вход + лесенка
TP1–TP4 до −100%) давала PF 0.5–0.74 (минус). Полная кампания с двумя входами и глубокой зоной B
оказалась хрупкой. Победил простой конфиг D: первый лимит-вход в зону A. BoS-подтверждение основного
входа ухудшало результат (PF 1.54 → 0.88). Финал: D3 (2 TP + безубыток@B), риск 0.5%, лимит 3 позиции
→ +252% / DD 33% за 6 мес.

**Что изменено:**
- `config.py`: `RISK_PER_TRADE` дефолт 1.0→0.5; `MAX_ACTIVE_PAIRS` 5→3; новые флаги `ENTRY_MODE='ZONE_LIMIT'`,
  `REQUIRE_BOS=False`, `USE_ZONE_B_ENTRY=False`, `BREAKEVEN_AT_B=True`; `TP_CLOSE_FRACTIONS=[0.5,0.5]`;
  `TRAIL_AFTER_TP=99` (трейлинг отключён); убраны `TP3_LEVEL`/`TP4_LEVEL`.
- `.env`: `RISK_PER_TRADE=0.5`, `MAX_ACTIVE_PAIRS=3`.
- `strategy.py`: `analyze_market` — вход GTC-лимитом на 38.2%-границе зоны A БЕЗ ожидания BoS
  (детект пред-входовой области: цена между границей зоны A и уровнем B). `calculate_trade_params`
  переписан под 2 TP (−18%/−27%) + `be_level` (уровень B). Зона B как точка входа отключена.
- `pair_scanner.py`: фильтр «цена в зоне» заменён на пред-входовую область зоны A; зона B убрана.
- `trade_manager.py`: GTC-лимит ставится на границе зоны A; `_place_sl_tp_orders` — 2 TP по 50%;
  `_check_tp_levels` — безубыток при пробое уровня B (0%), 2 TP; персистентность хранит `be_level`
  вместо TP3/TP4; восстановление TP по долям 50%.
- `trade_journal.py`/`telegram_notify.py`/`chart_generator.py`: устойчивы к отсутствию TP3/TP4,
  сообщения/график обновлены под 2 TP + безубыток.
- `bot.py`: убран лишний fetch 5M; лог-сообщения под лимит-вход.
- `backtest_campaign.py`: новый симулятор кампании (машина состояний, портфельный лимит, сетка
  риск×лимит) — инструмент валидации стратегии.

**Зачем:** Привести бота к методичке Фибоначчи в варианте, который статистически прибылен (PF ~1.5),
с контролируемой просадкой (риск 0.5% + лимит 3 позиции).

## [2026-06-27] — W7: Восстановление позиций после перезапуска

**Файлы:** `Live_Bot/trade_manager.py`, `Live_Bot/telegram_notify.py`

**Что добавлено:**
- Новый файл состояния `positions_state.json` — создаётся при открытии позиции, удаляется при закрытии
- Метод `_save_position_state()` — сохраняет все параметры открытой позиции на диск
- Метод `_remove_position_state()` — удаляет запись после закрытия позиции
- Метод `_load_positions_state()` — читает файл состояния
- Метод `_rebuild_position()` — восстанавливает полный dict позиции из биржевых данных + сохранённого состояния, вычисляет сколько TP уже сработало
- Метод `_restore_positions()` — вызывается при старте бота, сверяет `positions_state.json` с биржей через `fetch_positions()`, добавляет в `active_positions`
- Функция `positions_restored()` в `telegram_notify.py` — Telegram-уведомление о восстановленных позициях
- Вызов `_restore_positions()` в `__init__` TradeManager

**Зачем:** При краше или перезапуске бот терял контроль над открытыми позициями — не мог управлять SL/TP и трейлингом.

## [2026-06-27] — W9+: Система отложенных GTC ордеров (Вариант D, замена блокирующей версии)

**Файлы:** `Live_Bot/config.py`, `Live_Bot/trade_manager.py`, `Live_Bot/bot.py`, `Live_Bot/telegram_notify.py`

**Что изменено и добавлено:**

В `config.py`:
- Удалена константа `LIMIT_ORDER_TIMEOUT_SEC` (больше не нужна)
- Добавлена константа `PENDING_ORDER_MAX_HOURS = 4.0` — GTC ордер живёт до 4 часов

В `trade_manager.py`:
- Удалён метод `_place_limit_entry()` (блокирующий polling)
- Удалён `import time` (больше не нужен)
- Добавлен файл состояния `pending_orders.json` (константа `PENDING_ORDERS_FILE`)
- Добавлен статичный метод `_serialize_for_json()` — конвертация signal dict в JSON (обработка pandas Timestamp, numpy scalar, NaN)
- Добавлен метод `_load_pending_orders()` — читает pending_orders.json
- Добавлен метод `_save_pending_order()` — сохраняет GTC ордер с параметрами, сигналом, ценой инвалидации и сроком истечения
- Добавлен метод `_remove_pending_order()` — удаляет ордер из файла
- Добавлен метод `_cancel_pending_order()` — отменяет на бирже + удаляет из файла
- Добавлен метод `_restore_pending_orders()` — при старте бота проверяет pending ордера с биржей, регистрирует заполненные
- Добавлен метод `_register_filled_order()` — регистрирует заполненный GTC лимит как полную позицию (SL/TP, журнал, кулдаун, Telegram)
- Добавлен метод `check_pending_orders()` — вызывается каждые 5 минут, проверяет: срок истечения, инвалидацию по цене (88.6% уровень), достижение TP1 без заполнения, статус ордера на бирже
- Изменён `execute_trade()` — лимитный путь теперь неблокирующий: размещает GTC, сохраняет в pending_orders.json, немедленно возвращает `True`
- Изменены `get_active_count()` и `get_open_pairs()` — pending ордера учитываются как занятые слоты
- Добавлена проверка pending в `execute_trade()` — не открывать если для пары уже есть pending ордер

В `bot.py`:
- Добавлен вызов `trade_manager.check_pending_orders()` в `trading_cycle()` после `manage_active_positions()`
- Пересчёт `active_count`, `open_pairs`, `available` после проверки pending (заполнение могло изменить слоты)

В `telegram_notify.py`:
- Добавлена функция `limit_order_placed()` — уведомление о выставленном GTC лимите с ценой, стопом и временем ожидания

**Зачем:** Блокирующий polling на 2 минуты не давал поймать ретесты BoS (происходят через 10–60 мин), блокировал управление позициями, и market fallback давал плохие входы. GTC без блокирования решает всё это.

**Логика отмены pending ордера:**
1. Истёк срок (4 часа) → отменяем
2. Цена ушла ниже 88.6% уровня для LONG (или выше для SHORT) → сетап разрушен → отменяем
3. Цена достигла TP1 без заполнения → поезд ушёл → отменяем
4. Ордер отменён самой биржей → удаляем из файла
